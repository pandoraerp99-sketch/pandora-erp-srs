# 1. Resumen ejecutivo
Pandora ERP es un sistema de gestión de ventas SaaS desarrollado para el mercado argentino, con foco en comercios medianos que requieren facturación electrónica AFIP, integración con MercadoPago, y un panel de control moderno que permita la toma de decisiones en tiempo real. Este documento cubre de forma exhaustiva todos los aspectos técnicos, de seguridad, de negocio y operacionales del proyecto, con el objetivo de servir como referencia estratégica para el desarrollo y lanzamiento del producto.

INFO: El SRS v3.0 existente es sólido. Los gaps identificados son concretos y acotados. La doctrina correcta es: replicar la cultura operacional de Linear, Stripe y Cloudflare sin replicar su infraestructura.

# 3. Diseño y funcionalidad
El diseño del dashboard de Pandora es una ventaja competitiva real. El riesgo principal no es el diseño en sí mismo, sino la forma en que se cargan los datos que lo alimentan. Un dashboard visualmente excelente con datos lentos o inconsistentes destruye la confianza del usuario más rápido que un diseño mediocre con datos correctos.


## 3.1 Principios del diseño implementado
Dashboard principal con métricas en tiempo real: facturación, clientes activos, pipeline
Panel lateral de IA para consultas contextuales sobre el negocio
Reuniones y calendario integrados en la columna derecha
Acciones rápidas: nuevo deal, agregar contacto, nueva tarea, subir archivo
Navegación lateral con todas las secciones del ERP


## 3.2 Reglas para mantener calidad sin sacrificar performance

### 3.2.1 Skeletons obligatorios
Cada widget del dashboard debe tener su estado de carga con skeleton. Sin esto, los usuarios ven layouts rotos o en blanco mientras los datos llegan. Esto es especialmente crítico para los números de facturación en tiempo real.

ATENCIÓN: Regla: ningún componente del dashboard puede renderizarse sin un skeleton loader correspondiente. Esto aplica a todos los panels de métricas, gráficos y listas.


### 3.2.2 Server Components para datos pesados
En Next.js 16, los charts y KPIs se fetchean en el servidor como Server Components. El cliente recibe HTML ya renderizado. Esto elimina el flash de carga y es 2-3x más rápido que fetch desde el cliente.


### 3.2.3 Separación de datos en vivo vs históricos
Los datos deben clasificarse en dos categorías con estrategias distintas: datos en vivo (facturación del día, notificaciones) que usan Supabase Realtime subscriptions; y datos históricos (gráficos mensuales, comparativas) que usan queries con caché sobre tablas de resúmenes pre-agregados, no sobre las tablas de transacciones directamente.


### 3.2.4 Daily summaries pre-agregados (Fase 1)
Los gráficos de tendencia mensual no deben consultar la tabla de ventas completa en cada render. En Fase 1 se implementan tablas de resúmenes diarios pre-calculados que reducen las queries a lecturas simples de N filas por período.

CRÍTICO: Anti-patrón crítico: dashboards bonitos con datos de demo o sin datos reales generan pérdida de confianza inmediata. Mejor tener pocos KPIs reales que muchos charts vacíos.


# 4. Arquitectura de código
La arquitectura de código es la decisión más costosa de cambiar después del primer cliente real. Pandora usa un monolito modular en Next.js 16 con separación de capas. Este patrón permite evolucionar hacia microservicios en Fase 3+ sin reescribir el core del negocio.


## 4.1 Estructura de carpetas recomendada
La organización del código sigue el principio de "feature-first" dentro de las convenciones de Next.js App Router:
src/app/ — rutas Next.js App Router (pages, layouts, loading, error)
src/app/actions/ — Server Actions organizadas por dominio de negocio
src/components/ — componentes React reutilizables sin lógica de negocio
src/lib/ — utilidades, helpers, clientes de servicios externos
src/lib/services/ — lógica de negocio (SaleService, InvoiceService, etc.)
src/config/env.ts — configuración centralizada con validación Zod (CRÍTICO)
src/lib/errors.ts — taxonomía centralizada de errores
src/types/ — tipos TypeScript compartidos


## 4.2 Configuración por entorno — GAP CRÍTICO
Este es el gap más urgente identificado. Sin un sistema de configuración centralizado, los secretos pueden aparecer en logs, el staging puede conectarse a producción accidentalmente, y los errores de variables faltantes se descubren en producción.

CRÍTICO: src/config/env.ts con validación Zod es el primer archivo que debe escribirse antes de cualquier service. Todos los servicios dependen de esta configuración desde el día 1.

El archivo debe incluir categorías separadas: secretos (MP_ACCESS_TOKEN, SUPABASE_SERVICE_ROLE_KEY), variables públicas (NEXT_PUBLIC_*), configuración AFIP (env, certs, CUIT, timeout), y configuración de observabilidad (LOG_LEVEL, SENTRY_DSN). El proceso debe fallar en el arranque si cualquier variable requerida está ausente.


## 4.3 Taxonomía de errores
Cada error del sistema debe pertenecer a una categoría con código tipado. Esto permite que el frontend muestre mensajes útiles, que los logs sean consultables por código, y que el soporte entienda qué pasó sin acceso al stack trace.
VALIDATION_ERROR — datos inválidos del usuario
PERMISSION_DENIED — acceso no autorizado
NOT_FOUND — recurso inexistente
RATE_LIMIT_EXCEEDED — demasiadas requests
AFIP_ERROR — error en servicios AFIP (con sub-códigos)
MP_ERROR — error en MercadoPago (con sub-códigos)
INTERNAL_ERROR — error no esperado del sistema


## 4.4 State machines y máquinas de estado
El SRS v3.0 tiene 12 state machines formalizadas para los flujos críticos del negocio. Esto incluye el ciclo de vida de una venta, el proceso de facturación AFIP, el estado de un pago MP, y el proceso de cobro en POS. Ninguna transición de estado debe ocurrir fuera de estas máquinas.


## 4.5 Patrones a evitar
CRÍTICO: Los siguientes patrones están explícitamente prohibidos por los ADRs del SRS: microservicios antes de Fase 3, CQRS en el core, event sourcing, GraphQL público en F0, service mesh, Kubernetes, Kafka, Vault enterprise.


# 5. Base de datos
Pandora usa PostgreSQL a través de Supabase como única fuente de verdad. La arquitectura de datos es uno de los aspectos más costosos de modificar después del primer cliente real, por lo que las decisiones de schema, índices y multi-tenancy deben estar correctas desde Fase 0.


## 5.1 Multi-tenancy con Row Level Security
Toda la data de Pandora está aislada por empresa (tenant) usando RLS de PostgreSQL con auth.jwt(). Este patrón garantiza que un error en el código de aplicación no pueda filtrar datos entre tenants. El SRS tiene tests obligatorios de cross-tenant que deben ejecutarse en cada deploy.

CRÍTICO: RLS es la línea de defensa final para el aislamiento de datos. Debe estar activo en TODAS las tablas sin excepción. Una tabla sin RLS es una vulnerabilidad IDOR directa.


## 5.2 Índices críticos
Los índices deben crearse junto con las tablas, no después. Los índices más importantes para el performance del dashboard:
(company_id, created_at DESC) en sales, invoices, cash_movements
(company_id, status) en deals, tasks
(user_id, created_at DESC) en login_attempts
(company_id, date) en daily_summaries para gráficos de tendencia


## 5.3 Tablas de audit log
El audit log debe ser append-only e inmutable. Cada operación crítica (ventas, facturas, cambios de configuración) genera una entrada con: timestamp, user_id, company_id, action, before (JSON), after (JSON), correlation_id, ip_address. La columna before/after debe implementarse desde el principio porque agregarla después requiere backfill de datos históricos.


## 5.4 Tablas de movimientos append-only
Las tablas stock_movements y cash_movements son append-only por diseño. Nunca se actualiza ni elimina un movimiento — se crea un movimiento de corrección. Esto es equivalente a event sourcing parcial sin su complejidad de implementación.


## 5.5 Migraciones
Todas las migraciones deben ser: declarativas (usando herramientas de Supabase), reversibles siempre que sea posible, y ejecutadas con procedimientos de checklist en producción. Nunca ejecutar migraciones directamente en producción sin validar en staging primero. Las migraciones destructivas (DROP COLUMN, DELETE masivo) deben tener checklist con firma del responsable.


## 5.6 Backup y recovery
Supabase Pro incluye point-in-time recovery (PITR) hasta 7 días. Para Fase 0 esto es suficiente. El plan de recovery debe contemplar: tiempo de restauración estimado (RTO), pérdida máxima de datos aceptable (RPO), procedimiento paso a paso documentado, y al menos un test de restauración antes del lanzamiento.

ATENCIÓN: Verificar que el plan de Supabase contratado incluye PITR. El plan gratuito NO incluye backups automáticos con point-in-time recovery. Para un SaaS con datos financieros, esto no es negociable.


# 6. Seguridad integral
La seguridad de Pandora debe pensarse en capas concéntricas: la primera capa (autenticación) protege el acceso, la segunda (autorización) protege los recursos dentro del sistema, la tercera (validación) protege contra datos maliciosos, y la cuarta (monitoreo) detecta actividad anómala. Ninguna capa reemplaza a las otras.

## 6.2 Ataques de alta probabilidad para SaaS argentino

### 6.2.1 Credential stuffing
Uso de listas de contraseñas filtradas de otras plataformas para intentar acceder. Es el ataque más común contra aplicaciones de negocio. Mitigaciones: rate limiting de login (5 intentos/5 minutos por IP+email), leaked password protection de Supabase (integrado con HaveIBeenPwned), lockout progresivo, alerta por email en login desde IP nueva.


### 6.2.2 Webhook spoofing de MercadoPago
El atacante envía un POST al endpoint de webhooks simulando una notificación de pago confirmado sin haber pagado realmente. Es crítico para cualquier SaaS con pagos en Argentina. La mitigación es verificar la firma HMAC-SHA256 que MP incluye en cada webhook usando el MP_WEBHOOK_SECRET antes de procesar cualquier notificación.


### 6.2.3 Price tampering
El usuario modifica el precio de un producto en el cliente (DevTools, proxy) antes de enviarlo al servidor. Si el servidor confía en el precio enviado por el cliente, el atacante puede comprar productos a precio cero. La mitigación es simple: el servidor siempre recalcula el precio desde la base de datos usando el product_id, nunca usa el precio enviado por el cliente.


### 6.2.4 IDOR — Insecure Direct Object Reference
Un usuario autenticado accede a datos de otra empresa cambiando un ID en la URL o en el body de una request. Para Pandora, esto significaría ver deals, facturas o clientes de otro tenant. Está cubierto por RLS en Supabase, pero debe verificarse que TODAS las tablas tienen RLS activo y que ninguna Server Action hace queries sin el filtro de company_id.


### 6.2.5 XSS — Cross-Site Scripting
Un usuario malicioso ingresa código HTML o JavaScript en un campo de texto (nombre de empresa, descripción de producto, nota de deal) que luego se renderiza sin sanitizar. Next.js escapa el output por defecto, pero hay casos donde se usa dangerouslySetInnerHTML o se renderizan datos sin sanitizar. Mitigación: Content Security Policy estricta en los headers HTTP y validación con Zod en todos los inputs.


## 6.3 Security headers HTTP obligatorios
Los siguientes headers deben configurarse en next.config.js antes del primer deploy a producción:
Content-Security-Policy (CSP) — define qué recursos puede cargar la página
X-Frame-Options: DENY — previene clickjacking via iframe
X-Content-Type-Options: nosniff — previene MIME sniffing
Referrer-Policy: strict-origin-when-cross-origin — controla información de referrer
Strict-Transport-Security (HSTS) — fuerza HTTPS en futuros accesos
Permissions-Policy — deshabilita APIs del navegador no usadas (cámara, micrófono, etc.)


## 6.4 Gestión de secretos
Los secretos de la aplicación (tokens de API, credenciales AFIP, webhook secrets) deben gestionarse según estas reglas:
Nunca en el código fuente — nunca hardcodeados, ni en comentarios
Nunca en logs — Sentry debe tener scrubbing configurado para tokens y keys
Nunca en el cliente — todas las variables secretas son server-only
Entornos separados — staging tiene sus propios secretos, distintos de producción
Rotación documentada — procedimiento escrito para rotar cada secreto sin downtime


## 6.5 Compliance — Ley 25.326 Argentina
Pandora almacena datos personales de comerciantes y sus clientes (nombre, CUIT, dirección, datos de contacto). La Ley 25.326 de Protección de Datos Personales de Argentina establece obligaciones que aplican al proyecto:
Informar a los titulares qué datos se almacenan y con qué finalidad
Obtener consentimiento explícito para el tratamiento de datos sensibles
Implementar medidas de seguridad proporcionales a la sensibilidad de los datos
Permitir a los titulares acceder, rectificar y eliminar sus datos (derecho ARCO)
No transferir datos a terceros sin consentimiento previo

ATENCIÓN: Verificar con un asesor legal antes del lanzamiento público. Incumplir la Ley 25.326 puede resultar en multas y, más importante, en pérdida de confianza de los clientes.

# 8. Testing
La estrategia de testing de Pandora sigue el principio de pirámide: muchos tests unitarios rápidos, algunos tests de integración para los flujos críticos, y pocos tests E2E para los happy paths de negocio. El objetivo no es cobertura del 100% sino confianza en los flujos que generan dinero.


## 8.1 Qué testear primero (Fase 0)
Con recursos limitados, los primeros tests deben cubrir los flujos que, si fallan, generan consecuencias directas de negocio o legales:
Cálculo de totales y descuentos en ventas (errores de redondeo fiscal son un riesgo real)
Generación y validación de XML para AFIP
Lógica de estado de pagos MercadoPago
RLS cross-tenant: verificar que un usuario no puede ver datos de otra empresa
Rate limiting: verificar que se bloquea correctamente
Webhook signature verification de MP

Un pipeline de CI/CD bien configurado elimina errores humanos en el proceso de deploy y permite iterar rápido con confianza. Para un equipo pequeño como el de Pandora, la automatización del deploy es especialmente crítica porque no hay equipo de QA separado.

## 9.2 Pipeline de GitHub Actions
El pipeline recomendado para Pandora tiene tres etapas secuenciales:
Lint & Type check — Biome + TypeScript (< 30 segundos). Si falla, no continúa.
Unit & Integration tests — Vitest con Supabase local (< 2 minutos). Si falla, no continúa.
Deploy a staging — Vercel preview automático en cada PR (< 3 minutos).

Deploy a producción es manual con checklist. Auto-deploy a producción solo cuando cobertura de tests supere 80% y rollback automático esté probado.

## 10.2 Correlation IDs
Cada request debe tener un correlation_id único que se propaga a todos los logs, llamadas a AFIP, llamadas a MP, y eventos de error en Sentry. Esto permite "rastrear" una venta específica desde el click del cajero hasta el XML de AFIP, incluyendo todos los errores intermedios.


## 10.3 Health check endpoint
El endpoint GET /api/health debe retornar el estado de todas las dependencias críticas: conexión a Supabase, conectividad con AFIP (ping a homologación), conectividad con MP, y versión del deploy. Este endpoint es monitorizado por Uptime Robot cada 5 minutos y debe responder en menos de 2 segundos.


## 10.4 Alertas críticas
Las siguientes condiciones deben generar alertas inmediatas (email/Slack):
Tasa de errores 5xx superior al 1% en los últimos 5 minutos
Latencia del dashboard superior a 3 segundos
Health check falla 2 veces consecutivas
Error de conexión a Supabase o AFIP
Más de 10 errores de autenticación fallida desde la misma IP en 1 minuto
Transacción de venta sin confirmación de AFIP después de 60 segundos


# 11. Onboarding y activación de usuarios
El onboarding es el proceso por el cual un nuevo cliente pasa de registrarse a generar su primera venta real. Es la métrica de activación más importante del negocio. Sin un onboarding bien diseñado, la mayoría de los registros nunca llegan a ser clientes activos.


## 11.1 Activation tracking — GAP identificado
El SRS menciona onboarding wizard pero no tiene un sistema de tracking de activación que informe decisiones de retención. Esto significa que actualmente no hay forma de saber en qué paso los nuevos clientes abandonan el onboarding.

ATENCIÓN: Implementar activation tracking con PostHog con 5 eventos clave. Sin esto se opera a ciegas en retención. Tiene 4 horas de trabajo y ROI inmediato.


## 11.2 Eventos de activación recomendados
empresa_creada — completó el wizard de setup inicial
primer_producto_agregado — configuró al menos un producto
primer_cliente_creado — agregó su primer cliente
primera_venta_creada — procesó su primera venta
primera_factura_emitida — emitió su primera factura AFIP

La secuencia empresa_creada → primera_factura_emitida define el "momento AHA" del producto. El tiempo entre estos dos eventos es la métrica de activación principal. Si supera 7 días, el onboarding tiene un problema que debe resolverse.


## 11.3 Wizard de setup
El wizard de onboarding debe completarse en menos de 10 minutos. Los pasos sugeridos son:
Datos de la empresa (CUIT, razón social, condición IVA, dirección fiscal)
Configuración AFIP (certificado, punto de venta)
Primer producto o servicio
Primer cliente (o saltear para probar con datos de demo)
Tour guiado del dashboard de 2 minutos

# 13. Accesibilidad
La accesibilidad de Pandora impacta tanto en la inclusión de usuarios con discapacidades como en la calidad general del código y la experiencia de usuario. shadcn/ui está construido sobre Radix UI, que incluye accesibilidad por defecto en sus componentes.


## 13.1 Estado actual
El uso de shadcn/ui y Radix UI proporciona accesibilidad de base en los componentes de UI. Sin embargo, hay aspectos que deben verificarse manualmente:
Contraste de colores — el diseño usa grises y purples que deben verificarse contra WCAG AA (ratio 4.5:1 mínimo)
Navegación por teclado — crítica para el POS donde los operadores usan atajos F1-F12 según el SRS

Landmarks y estructura semántica del HTML


## 13.2 POS keyboard-first
El SRS tiene una tabla completa de atajos F1-F12 para el POS. Esta es una característica de accesibilidad operacional: permite a cajeros operar sin ratón durante el horario pico de ventas, reduciendo el tiempo por transacción y los errores de operación.

### Fase 2 — 200 a 2000 clientes activos
Supabase Team o equivalente con read replicas
Pre-aggregation jobs para analytics del dashboard
OpenTelemetry para tracing distribuido
CDN optimizado para assets estáticos de clientes


### Fase 3+ — más de 2000 clientes activos
Evaluar extracción de servicios de alta carga como microservicios
Multi-región si la base de clientes se expande fuera de Argentina
Database sharding si Supabase Team alcanza sus límites

CRÍTICO: Lo que NO debe hacerse en ninguna fase antes de que sea necesario: Kubernetes, Kafka, service mesh, event sourcing en el core, CQRS, multi-región preventivo, microservicios tempranos.

# 19. Conclusiones y próximos pasos
Pandora tiene una base arquitectónica sólida documentada en el SRS v3.0 con 17 ADRs. El diseño de UI es una ventaja competitiva real. El stack tecnológico es el correcto para el momento y el equipo. Los gaps identificados son concretos, acotados, y resolubles en días de trabajo, no semanas.


## 19.1 Los 3 riesgos principales hoy
CRÍTICO: Riesgo 1 — Seguridad: los 4 gaps críticos (JWT en Server Actions, rate limiting, firma MP, security headers) deben resolverse antes del primer cliente real. Un incidente de seguridad en Fase 0 puede terminar el proyecto.

CRÍTICO: Riesgo 2 — Configuración: env.ts sin Zod significa que secretos pueden filtrarse en logs, que staging puede conectarse a producción, y que errores de variables se descubren en producción. Es el primer archivo que debe existir.

ATENCIÓN: Riesgo 3 — Procrastinación documental: el proyecto tiene documentación de primer nivel. Lo que falta es código. Cada semana sin clientes reales es una semana sin feedback de producto.


## 19.2 La única métrica que importa hoy
Todo lo analizado en este documento converge en una sola pregunta: ¿cuándo tiene Pandora su primer cliente pagando facturas reales en producción? Esa es la métrica que convierte este proyecto de un análisis arquitectónico excelente en un negocio.

El objetivo de Fase 0 es claro: 5 clientes activos generando facturación electrónica real. Todo lo que no contribuye directamente a ese objetivo en las próximas 6 semanas debe esperar.
